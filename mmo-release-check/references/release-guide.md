# 릴리스와 라이브 운영 가이드

## 목차

1. 매니페스트
2. 규칙 설명

4. 릴리스 체크리스트

## 1. 매니페스트

빌드에 들어간 입력을 해시해 기록한 파일이다.

| 항목 | 내용 |
|---|---|
| `build` | 빌드 번호 |
| `protocol_version` | 접속 시 교환하는 프로토콜 버전 |
| `protocol_hash`, `protocol_files` | `.fbs` 파일과 `protocol.lock.json`의 해시 |
| `data_hash`, `data_files` | 기획 데이터 폴더의 `.csv`, `.json` 해시 |
| `map_versions` | 맵별 서버 데이터 버전 (`ue-server-data-export`가 만든 값) |

줄 끝 문자(CRLF/LF) 차이는 해시에 영향을 주지 않는다. 윈도우와 리눅스에서 받은 같은 파일은 같은 해시가 된다.

## 2. 규칙 설명

| ID | 의미 | 대응 |
|---|---|---|
| REL001 | 매니페스트를 읽을 수 없다 | `make`로 다시 만든다 |
| REL002 | 프로토콜 정의나 프로토콜 버전이 클라이언트와 서버에서 다르다 | 같은 커밋에서 양쪽을 다시 빌드한다. 패킷이 어긋나 접속 직후부터 깨진다 |
| REL003 | 기획 데이터가 다르다 | 같은 커밋에서 다시 빌드한다. 클라이언트 표시와 서버 계산이 달라진다 (툴팁의 피해량과 실제 피해량) |
| REL004 | 맵 버전이 다르다 | 서버용 월드 데이터를 다시 내보내고 양쪽을 빌드한다. 벽 통과, 허공의 몬스터 |
| REL005 | 빌드 번호가 이전 릴리스와 같은데 내용이 다르다 | 빌드 번호를 올린다. 같은 번호의 서로 다른 빌드는 문제 추적을 불가능하게 한다 |
| REL006 | 검사 파이프라인이 통과하지 않았거나 보고서가 없다 | 실패한 검사를 먼저 해결한다 |
| REL007 | 프로토콜 정의가 바뀌었는데 프로토콜 버전이 그대로다 | 버전을 올린다. 올리지 않으면 옛 클라이언트가 거부당하지 않고 접속해 깨진 패킷을 주고받는다 |
| REL008 | 이전 릴리스와 프로토콜, 데이터, 맵이 모두 같다 | 코드만 바뀐 릴리스가 맞는지 확인한다. 데이터 변경이 빠졌을 수 있다 |

## 3. 버전 규칙

- **빌드 번호:** 릴리스마다 올린다. 클라이언트와 서버가 같은 번호를 쓴다.
- **프로토콜 버전:** `.fbs`가 바뀌면 올린다. 호환되는 변경(필드 추가)이어도 올린다. 서버가 허용하는
  클라이언트 버전 범위를 따로 관리하면 호환 변경 때 옛 클라이언트를 받아 줄 수 있다.
- **데이터 버전:** 데이터 해시가 그 역할을 한다. 접속 시 클라이언트가 자기 데이터 해시를 보내고
  서버가 다르면 패치를 요구한다.
- **맵 버전:** 접속 시 비교한다(`ue-server-data-export`의 가이드).

## 4. 릴리스 체크리스트

빌드 전:

- [ ] 릴리스 브랜치가 정해졌고 그 뒤로 들어간 변경이 모두 의도한 것이다
- [ ] `mmo-ci-pipeline`의 nightly 단계가 통과했다
- [ ] 프로토콜이 바뀌었으면 프로토콜 버전을 올렸다
- [ ] 맵이 바뀌었으면 서버용 월드 데이터를 다시 내보냈다

빌드 후:

- [ ] 클라이언트와 서버를 같은 커밋에서 빌드했다
- [ ] `check_release.py compare`가 통과했다
- [ ] 내부 서버에 올려 접속, 이동, 전투, 거래, 탑승을 직접 해 봤다
- [ ] 성능 캡처를 마을과 대규모 전투 장면에서 했다 (`ue-perf-budget-check`)

배포 전:

- [ ] 데이터베이스 변경이 있으면 변경 스크립트와 되돌리는 스크립트가 모두 준비되어 있다
- [ ] 데이터베이스를 백업했다
- [ ] 점검 공지를 올렸다 (시작과 종료 예정 시각, 변경 내용)
- [ ] 롤백 기준과 담당자가 정해져 있다 (7절)
- [ ] 이전 릴리스의 빌드와 매니페스트를 보관하고 있다

## 5. 점검(서버 내림) 체크리스트

- [ ] 점검 30분 전, 10분 전, 1분 전에 게임 안에서 알렸다
- [ ] 새 접속을 막았다
- [ ] 진행 중인 거래와 우편, 경매 정산이 끝나기를 기다리거나 안전하게 중단시켰다
- [ ] 모든 캐릭터를 저장한 뒤 서버를 내렸다. 저장 완료를 로그로 확인했다
- [ ] 데이터베이스 변경을 적용하고 결과를 확인했다
- [ ] 서버를 올리고 내부 계정으로 먼저 접속해 확인했다
- [ ] 접속을 열고 접속자 수, 오류 로그, 서버 부하를 30분간 지켜봤다

## 6. 핫픽스

급한 수정일수록 건너뛰기 쉬운 것들:

- [ ] 수정 범위가 최소다. 다른 변경이 함께 들어가지 않았다
- [ ] 클라이언트 패치 없이 서버만 바꾸는 경우, 프로토콜과 데이터가 클라이언트와 여전히 일치한다
      (`compare`를 돌린다. 서버 데이터만 바꾸면 `REL003`이 나온다. 그 차이가 의도한 것인지 확인한다)
- [ ] 서버만 데이터를 바꿔도 되는 값인지 확인했다. 클라이언트가 표시에 쓰는 값이면 표시와 실제가 어긋난다
- [ ] 관련 검사를 돌렸다 (`mmo-ci-pipeline`의 precommit 단계)
- [ ] 빌드 번호를 올렸다

악용 중인 버그(아이템 복사, 골드 증식)는 수정보다 차단이 먼저다. 해당 기능을 서버 설정으로 끄고,
로그로 영향 범위를 확인한 뒤 수정과 회수를 진행한다.

## 7. 롤백

롤백 기준을 릴리스 전에 정한다. 예:

- 접속 불가나 크래시가 다수 발생
- 재화나 아이템이 복사되는 문제
- 데이터 손상

절차:

1. 새 접속을 막고 점검을 공지한다.
2. 서버를 이전 빌드로 되돌린다. 보관한 이전 매니페스트로 클라이언트와 맞는지 확인한다.
3. 데이터베이스: 구조 변경이 있었으면 되돌리는 스크립트를 적용한다. 릴리스 후 쌓인 플레이 기록을
   버릴지 살릴지가 가장 어려운 결정이다. 백업 시점으로 되돌리면 그 사이의 진행이 사라진다.
4. 클라이언트: 이미 패치된 클라이언트는 되돌리기 어렵다. 서버가 새 클라이언트를 받아 줄 수 있는지가
   롤백 가능 여부를 정한다. 그래서 프로토콜은 호환되는 방향으로만 바꾸는 것이 유리하다
   (`mmo-protocol-check`의 호환 규칙).
5. 원인을 고친 뒤 새 빌드 번호로 다시 릴리스한다.

재화 문제는 롤백 없이 회수로 해결하는 편이 피해가 적다. 서버가 재화와 아이템의 생성과 소멸을 전부
기록하고 있어야 가능하다.

## 8. 검사가 보지 못하는 것

- 빌드 결과물이 매니페스트의 입력에서 실제로 만들어졌는지
- 서버 설정 파일, 데이터베이스 구조의 일치
- 코드의 변경 (해시 대상이 아니다)
- 클라이언트 에셋(메시, 텍스처)의 변경
