# 자체 서버 프로젝트의 넷코드 가이드

이 프로젝트는 자체 서버를 쓴다. 언리얼은 클라이언트이고, 서버와는 자체 프로토콜로 통신한다.
클라이언트 네트워크 코드나 패킷 처리 코드를 작성/리뷰할 때 읽는다.

## 목차

1. 언리얼 복제와 무엇이 다른가
2. 클라이언트 구조
3. 패킷 설계 체크리스트
4. 서버 검증 체크리스트
5. 이동 동기화
6. 서버가 월드를 알게 하는 방법
7. 흔한 실수

## 1. 언리얼 복제와 무엇이 다른가

| 언리얼 복제를 쓸 때 | 자체 서버일 때 |
|---|---|
| `Replicated` 프로퍼티가 자동으로 전달된다 | 상태 변경 패킷을 직접 정의하고 보낸다 |
| RPC로 호출한다 | 요청/응답/알림 패킷을 직접 정의한다 |
| 관련성, 우선순위를 엔진이 처리한다 | 관심 영역 관리를 서버에서 직접 만든다 |
| 캐릭터 이동 예측과 보정이 내장되어 있다 | 클라이언트 예측, 보간, 서버 보정을 직접 만든다 |
| 서버가 같은 맵을 로드한다 | 서버용 충돌/내비 데이터를 따로 내보낸다 |

원칙은 같다. 서버가 결정하고, 클라이언트가 보낸 값은 모두 의심하고, 필요한 만큼만 보낸다.

## 2. 클라이언트 구조

- **네트워크 스레드와 게임 스레드를 분리한다.** 소켓 수신과 패킷 해석은 별도 스레드에서 하고,
  액터와 UObject를 건드리는 처리는 큐에 넣어 게임 스레드에서 한다. 게임 스레드 밖에서 UObject를
  만지면 크래시가 난다.
- **패킷 처리량에 프레임당 상한을 둔다.** 밀집 상황에서 한 프레임에 수백 개가 몰리면 히치가 된다.
  시간 예산(예: 프레임당 2ms)을 넘으면 다음 프레임으로 넘긴다.
- **액터 생성/제거를 풀링한다.** 관심 영역에 들어오고 나가는 캐릭터마다 스폰/디스트로이하면
  밀집 지역에서 히치가 난다.
- **네트워크 계층을 게임 로직과 분리한다.** 패킷 핸들러는 데이터를 게임 쪽 시스템에 넘기기만 한다.
  핸들러 안에 게임 규칙을 넣지 않는다.
- 언리얼의 `Replicated`, RPC 지정자는 게임플레이 동기화에 쓰지 않는다. 코드에 보이면 의도를 확인한다.

## 3. 패킷 설계 체크리스트

- [ ] 패킷마다 고유 ID가 있고, ID는 한번 정하면 재사용하지 않는다.
- [ ] 프로토콜 버전을 접속 시 교환하고, 맞지 않으면 접속을 거부한다.
- [ ] 클라이언트와 서버가 같은 정의 파일에서 코드를 생성한다. 양쪽에 손으로 따로 적지 않는다.
- [ ] 클라이언트→서버 패킷에 결과 값(피해량, 획득 골드, 경험치, 최종 위치 확정)이 없다. 의도만 담는다.
- [ ] 가변 길이 필드(문자열, 배열)에 최대 길이가 있고 서버가 검사한다.
- [ ] 자주 보내는 패킷(이동, 상태 갱신)은 크기를 줄였다: 좌표 양자화, 변화분만 전송, 비트 플래그.
- [ ] 반드시 도착해야 하는 것(거래, 아이템 획득)과 버려도 되는 것(이동 갱신, 연출)을 구분해 전송한다.
- [ ] 패킷마다 초당 허용 횟수가 정해져 있다.

## 4. 서버 검증 체크리스트

클라이언트→서버 패킷 핸들러마다 확인한다.

- [ ] 보낸 세션이 그 캐릭터의 소유자인가
- [ ] 캐릭터가 그 행동을 할 수 있는 상태인가 (생존, 기절 아님, 거래 중 아님)
- [ ] 대상이 존재하고, 사거리와 시야 안에 있는가 (서버가 아는 위치 기준)
- [ ] 쿨다운, 자원(마나, 재화), 보유 아이템을 서버 데이터로 확인했는가
- [ ] 수량과 인덱스가 범위 안인가 (음수, 0, 오버플로 포함)
- [ ] 호출 빈도가 허용치 안인가
- [ ] 같은 요청이 두 번 와도 한 번만 처리되는가 (재전송, 중복 클릭)

## 5. 이동 동기화

- 클라이언트는 입력이나 목표 지점을 보내고 자기 캐릭터를 먼저 움직인다(예측).
- 서버는 속도 상한, 지형 통과 여부를 검사하고 확정 위치를 돌려준다.
- 차이가 작으면 클라이언트가 부드럽게 맞추고, 크면 서버 위치로 되돌린다.
- 다른 캐릭터는 받은 위치들 사이를 약간 지연해서 보간한다. 받은 위치로 바로 옮기면 끊겨 보인다.
- 언리얼의 `CharacterMovementComponent`는 로컬 이동과 충돌에 쓸 수 있지만, 내장 네트워크 보정은
  언리얼 서버를 전제로 하므로 쓰지 않는다.

## 6. 서버가 월드를 알게 하는 방법

자체 서버는 언리얼 맵을 로드하지 못한다. 이동 검증과 AI 길 찾기에 필요한 데이터를 내보내야 한다.

- 내비메시: 언리얼에서 빌드한 내비메시를 내보내 서버의 길 찾기 라이브러리가 읽게 한다.
- 충돌: 높이맵이나 단순화한 충돌 메시를 내보낸다. 서버는 정밀 충돌 대신 단순한 검사를 한다.
- 스폰 지점, 트리거 볼륨, 지역 경계: 레벨에서 추출해 데이터 파일로 내보낸다.
- 맵이 바뀔 때마다 내보내기가 자동으로 돌아야 한다. 클라이언트 맵과 서버 데이터가 어긋나면
  벽을 통과하거나 허공에 몬스터가 선다. 로드맵의 `ue-server-data-export`가 이 검사를 맡는다.

## 7. 흔한 실수

- 클라이언트가 계산한 피해량을 서버가 그대로 적용한다.
- 클라이언트가 보낸 위치를 검사 없이 믿는다 (순간 이동, 속도 핵).
- 패킷 핸들러에서 바로 액터를 스폰해 밀집 지역에서 프레임이 떨어진다.
- 클라이언트와 서버의 패킷 정의가 따로 관리되어 필드 순서가 어긋난다.
- 서버의 내비/충돌 데이터가 옛 맵 기준이다.
- 접속이 끊겼다 다시 붙을 때의 상태 복구를 나중으로 미룬다.
