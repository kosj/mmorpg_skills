# 규칙 설명과 수정 방법

| ID | 의미 | 고치는 방법 |
|---|---|---|
| PROTO001 | 두 패킷의 `packet_id`가 같다 | 새 패킷에 쓰지 않은 번호를 준다. lock 파일의 `packets`에 없는 번호여야 한다 |
| PROTO002 | 패킷인데 `packet_id`가 없거나 범위 밖이거나, 방향을 알 수 없다 | `(packet_id: N)`을 붙이고, 이름을 `C2S_`/`S2C_`로 시작하거나 `dir: "c2s"`를 붙인다 |
| PROTO003 | 예전에 다른 패킷이 쓴 번호를 다시 썼거나, 기존 패킷의 번호를 바꿨다 | 번호를 되돌리거나 새 번호를 쓴다. 옛 클라이언트가 그 번호를 옛 패킷으로 해석한다 |
| PROTO004 | 클라이언트→서버 패킷에 결과 값(피해량, 골드, 경험치 등) 필드가 있다 | 필드를 지우고 의도만 보낸다(스킬 ID, 대상 ID, 슬롯 번호). 수치는 서버가 계산한다 |
| PROTO005 | 클라이언트→서버 패킷의 문자열/배열에 `max_len`이 없다 | `(max_len: N)`을 붙인다. 서버는 생성된 헤더의 상수로 길이를 검사한다 |
| PROTO006 | 클라이언트→서버 패킷에 `rate`가 없다 | `(rate: N)`으로 초당 허용 횟수를 적는다. 서버가 이 값으로 빈도를 제한한다 |
| PROTO007 | 이전 버전과 호환이 깨지는 변경 | 아래 "호환되는 변경" 참조 |
| PROTO008 | 선언하지 않은 사용자 속성을 썼다 | 스키마 위쪽에 `attribute "이름";`을 추가한다. 없으면 flatc가 실패한다 |
| PROTO009 | 필드 이름만 바뀌었다 | 바이너리는 호환된다. 클라이언트와 서버 코드를 함께 고쳤는지만 확인한다 |
| PROTO010 | lock 파일이 없어 PROTO003, PROTO007을 건너뛰었다 | `--update-lock`으로 만들고 소스 컨트롤에 넣는다 |

## 호환되는 변경과 깨지는 변경

| 변경 | table | struct | enum |
|---|---|---|---|
| 맨 끝에 필드/값 추가 | 가능 | 불가 | 가능 |
| 필드/값 삭제 | 불가. `(deprecated)`로 표시 | 불가 | 불가 |
| 순서 변경, 중간에 삽입 | 불가 (모든 필드에 `id:`를 명시했다면 가능) | 불가 | 값이 바뀌면 불가 |
| 타입 변경 | 불가 | 불가 | 기반 타입 변경 불가 |
| 이름 변경 | 바이너리는 호환, 코드는 수정 필요 | 불가로 취급 | 불가로 취급 |

struct는 바꿀 수 없으므로 좌표처럼 영원히 고정될 것에만 쓴다. 바뀔 여지가 있으면 table로 만든다.

## PROTO004 예시

나쁜 예:

```
table C2S_UseSkill (packet_id: 1002, rate: 10) {
  skill_id: uint;
  target_id: ulong;
  damage: int;      // 클라이언트가 피해량을 정한다
}
```

좋은 예: 피해량은 서버가 계산해 `S2C_SkillResult`로 알린다.

```
table C2S_UseSkill (packet_id: 1002, rate: 10) {
  skill_id: uint;
  target_id: ulong;
}
```

`count`, `slot`, `id`처럼 클라이언트가 고르는 값은 괜찮다. 다만 서버가 범위와 소유를 검사해야 한다.

## 오탐 처리

필드 이름만 보고 내는 경고라 틀릴 수 있다. 의도한 것이면 그 줄이나 윗줄에 이유를 적는다.

```
// protolint:ignore PROTO004 정렬 기준일 뿐 서버 계산에 쓰지 않음
sort_by_price: bool;
```

의심 단어 목록은 `protocol-config.json`의 `authoritative_field_tokens`에서 조정한다.
단어는 밑줄과 대소문자 경계로 나눠 비교한다(`gold_amount`의 `gold`는 걸리고 `expected_slot`의 `exp`는 걸리지 않는다).

## 이 검사기가 보지 못하는 것

- 스키마 문법 오류: flatc가 잡는다.
- 서버 핸들러가 실제로 검증하는지: `mmo-netcode-review`의 서버 검증 체크리스트로 본다.
- `max_len`, `rate`가 서버 코드에서 실제로 적용되는지: 생성된 헤더를 쓰는지 코드 리뷰로 확인한다.
- 중첩 구조의 총 크기: 패킷 전체 크기 상한은 프레이밍 계층에서 따로 건다.
