## 1. 단계 구성

| 단계 | 언제 | 무엇을 | 걸리는 시간 |
|---|---|---|---|
| precommit | 커밋이나 제출 전, 개발자 PC | 에디터 없이 도는 검사 중 바뀐 파일과 관련된 것 | 수 초 |
| nightly | 야간 빌드, 빌드 머신 | 모든 검사. 에디터가 수집한 파일의 판정 포함 | 수집 시간에 달림 |

| 검사 | precommit | nightly | 에디터 필요 |
|---|---|---|---|
| 기획 데이터 (`mmo-data-check`) | O | O | 아니오 |
| 전투 스킬 데이터 (`mmo-combat-skill`) | O | O | 아니오 |
| 프로토콜 (`mmo-protocol-check`) | O | O | 아니오 |
| 언리얼 복제 문법 유입 (`mmo-netcode-review`) | O | O | 아니오 |
| 클라이언트 연결 규약 (`ue-client-contract`) | O | O | 아니오 |
| 서버용 월드 데이터 (`ue-server-data-export`) | O | O | 판정은 아니오. 내보내기는 필요 |
| 에셋 규격 (`ue-asset-spec-check`) |  | O | 수집에 필요 |
| 성능 예산 (`ue-perf-budget-check`) |  | O | 캡처에 게임 실행 필요 |
| 스킬 팩 단위 테스트 | O | O | 아니오 |

## 2. 설정 파일

`pipeline.json`의 구조:

- `vars`: 경로 변수. `{이름}`으로 다른 곳에서 쓴다. `root`는 프로젝트 최상위이고 나머지 경로는 그 기준이다.
- `checks`: 검사 목록.
  - `id`, `title`
  - `stages`: 이 검사가 속한 단계
  - `triggers`: 이 패턴에 맞는 파일이 바뀌었을 때만 실행한다. 없으면 항상 실행한다
  - `inputs`: 실행 전에 있어야 하는 경로. 없으면 실행하지 않고 "입력 없음"이 된다
  - `required`: 기본 true. false면 "입력 없음"을 실패로 세지 않는다
  - `command`: 실행할 명령. `{python}`은 지금 쓰는 Python으로 바뀐다
  - `timeout_sec`: 기본 600
- `co_change`: 함께 바뀌어야 하는 파일 규칙 (7절)

패턴: `**/`는 0개 이상의 폴더, `**`는 모든 문자, `*`는 폴더를 넘지 않는 문자열.

실행할 때 `--var 이름=값`으로 변수를 덮어쓸 수 있다. 빌드 머신과 개발자 PC의 경로가 다를 때 쓴다.

## 3. 상태 값

| 상태 | 의미 | 전체 결과 |
|---|---|---|
| 통과 (pass) | 검사가 종료 코드 0으로 끝났다 | |
| 실패 (fail) | 검사가 종료 코드 1로 끝났다. error가 있다 | 실패 |
| 실행 오류 (error) | 종료 코드가 0, 1이 아니다. 입력 파일이 틀렸거나 스크립트가 죽었다 | 실패 |
| 시간 초과 (timeout) | 제한 시간 안에 끝나지 않았다 | 실패 |
| 입력 없음 (missing_input) | `inputs`의 경로가 없다 | 필수 검사면 실패 |
| 해당 없음 (not_triggered) | 바뀐 파일이 이 검사와 관련 없다 | |

"해당 없음"과 "입력 없음"은 검사가 돌지 않은 것이다. 통과로 세지 않는다.

## 4. 커밋 전 훅

Git을 쓸 때 `.git/hooks/pre-push`의 예 (실행 권한 필요):

```sh
#!/bin/sh
python Skills/mmo-ci-pipeline/scripts/run_checks.py \
    --pipeline Skills/mmo-ci-pipeline/references/pipeline.json \
    --stage precommit --git-base origin/main --md Saved/CheckReports/summary.md
```

- 커밋마다 돌리면 번거로우므로 push 전에 건다. 실패하면 push가 막힌다.
- 훅은 개인 PC에만 적용되고 건너뛸 수 있다. 같은 검사를 서버(풀 리퀘스트 검사)에서도 돌려야 강제된다.
- Perforce를 쓰면 제출 전 트리거나 제출 도구에서 바뀐 파일 목록을 파일로 만들어 `--changed-files`로 준다.
- 큰 바이너리 에셋 때문에 Git LFS나 Perforce를 쓰는 경우가 많다. 소스 컨트롤이 정해지면
  `mmorpg-router/references/project-context.md`에 기록한다.

## 5. 야간 빌드

순서:

1. 최신 소스를 받는다.
2. 에디터 수집: 에셋 규격의 `run_check.py`, 월드 데이터의 `collect_level_data.py`를 커맨드릿으로 실행한다.
3. 게임 빌드 후 성능 캡처: 정해진 장면(마을, 대규모 전투, 필드 이동, 던전)을 자동으로 돌려 CSV를 만든다.
4. `run_checks.py --stage nightly`를 실행한다. 바뀐 파일 목록을 주지 않으므로 모든 검사가 돈다.
5. 보고서를 팀 채널이나 메일로 보낸다. 실패한 검사와 담당 스킬 이름을 함께 적는다.

- 2, 3단계가 실패하면 판정할 파일이 없어 "입력 없음"이 된다. 에셋과 성능 검사는 `required`가 false라
  실패로 세지 않으므로, 수집 단계의 성공 여부는 빌드 시스템에서 따로 확인한다.
- 성능 검사는 이전 날의 보고서를 `--baseline`으로 주면 악화를 잡는다. `pipeline.json`의 명령에 추가한다.
- 야간 빌드가 며칠째 실패한 채로 방치되면 아무도 보지 않게 된다. 실패는 다음 날 안에 고치거나,
  고칠 수 없으면 그 검사의 기준을 조정하는 결정을 내린다.

## 6. 검사 추가 방법

1. 검사 스크립트가 종료 코드 약속을 지키는지 확인한다: 0 통과, 1 실패, 그 밖은 입력 문제.
2. `pipeline.json`의 `checks`에 항목을 추가한다. 경로는 `vars`에 변수로 둔다.
3. `--list`로 계획에 나오는지, `--only <id>`로 그 검사만 돌려 본다.
4. 에디터 없이 돌고 빠르면 precommit에, 아니면 nightly에만 넣는다.

스킬 팩의 새 검사 스킬은 이 약속을 따르게 되어 있다(`mmorpg-router`의 스킬 작성 규칙).

## 7. 함께 바뀌어야 하는 파일 규칙

검사 스크립트가 원리상 잡을 수 없는 누락을 잡는다. 바뀐 파일 목록만으로 판정한다.

| 규칙 | 뜻 |
|---|---|
| 맵이 바뀌면 서버용 월드 데이터도 바뀌어야 한다 | 맵만 고치고 내보내기를 하지 않으면 서버 데이터와 클라이언트 버전 파일이 둘 다 옛 상태로 일치해서, 월드 데이터 검사 자체는 통과한다. 이 규칙만 그 경우를 잡는다 |
| 서버용 월드 데이터가 바뀌면 클라이언트 버전 파일도 바뀌어야 한다 | 한쪽만 올리면 그 사이의 빌드가 어긋난다 |
| 패킷 정의가 바뀌면 lock 파일도 바뀌어야 한다 | lock을 갱신하지 않으면 다음 사람의 호환성 검사가 옛 기준으로 돈다 |

- 맵을 고쳤지만 서버에 영향이 없는 변경(조명, 장식)도 이 규칙에 걸린다. 내보내기를 다시 하면 내용이
  같아 버전이 바뀌지 않으므로 서버 데이터 파일은 바뀌지 않는다. 이런 경우가 잦으면 맵을 고친 사람이
  "서버 영향 없음"을 표시하는 방법(커밋 메시지 태그 등)을 정하고 규칙에 예외를 추가한다.
- 맵 파일의 경로 패턴(`Content/**/*.umap`, 외부 액터 폴더)은 프로젝트 구조에 맞게 고친다.
